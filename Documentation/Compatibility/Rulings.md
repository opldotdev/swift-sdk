# Compatibility rulings

Status: Approved for implementation after the detailed Fable readiness review.

The default precedence is network consensus and applicable BRC requirements,
then accepted cross-SDK vectors, then incidental Go SDK behavior. When one BRC
document contradicts its own vectors, a newer governing BRC, or an established
wire implementation, the exact exception is recorded here rather than hidden
behind the general rule.

| ID | Conflict | Proposed Swift behavior | Reason and test obligation |
| --- | --- | --- | --- |
| COMP-001 | CompactSize decoding in Go accepts non-minimal forms and some callers use max-u64 as “-1”. | Provide bounded permissive and canonical-required decoding policies. Encode canonically. Model max-u64 absence as a named sentinel only in formats that specify it; never as an ordinary length. | Preserves wire import compatibility without allowing ambiguous canonical output or unbounded allocation. Test every prefix boundary, truncation, non-minimal form, max-u64, and per-call maximum. |
| COMP-002 | BRC-2 prose describes a shared-secret hash input that disagrees with the published vectors and Go. | Follow the published vectors and Go v1.3.3 padded-x-coordinate derivation for the AES-GCM key. Mark the prose conflict and do not offer a second silent variant. The HMAC key is ruled separately by COMP-065. | The vectors are interoperable evidence. Test exact ciphertext, plaintext, HMAC, wrong counterparty/protocol/key ID, tag tampering, and IV/tag truncation. |
| COMP-003 | BRC-30 says four-byte source satoshis; Go and Bitcoin amounts use eight bytes. | Parse and emit unsigned 64-bit little-endian source amounts. Do not emit the ambiguous four-byte form. | Matches Go Extended Format and the transaction amount domain. Test Go↔Swift bytes and overflow/truncation. |
| COMP-004 | BRC-43 gives 280/1033 limits; BRC-100 and Go use 400/800. Go's Unicode-aware trimming and lowercasing can also admit names outside a stable ASCII derivation profile. BRC-44 reserves `admin` protocols for trusted wallet internals. | Use protocol names of 5…400 UTF-8 bytes and key IDs of 1…800 UTF-8 bytes. Protocol names trim ASCII whitespace, lowercase ASCII, allow only letters, digits, and single spaces, reject the `admin` prefix and ` protocol` suffix, and do not normalize key IDs. The one wallet-internal WPM metadata identifier is available only as the explicit `WalletProtocolID.walletMetadataEncryption` constant; generic construction and application JSON/wire encoding and decoding continue to reject it. | Newer wallet limits and the parity baseline agree. The stricter Swift identifier policy fails closed rather than deriving a different key from Unicode or reserved-name artifacts. The named constant makes the wallet-internal exception auditable without widening external encoders or decoders. Tests cover byte boundaries, every ASCII character, Unicode rejection, reserved names, exact local fields and ProtoWallet output, boundary rejection, and distinct composed/decomposed key IDs. |
| COMP-005 | BRC-48 specifies lock-after PushDrop; Go creates both but decodes only lock-before. | Decode and construct spec-conformant lock-after. Support lock-before through an explicitly named compatibility mode. | Achieves BRC conformance without losing Go ecosystem inputs. Test that no auto-detection ambiguity changes pushed data. |

| COMP-010 | Go inscription comments call ordinals BRC-43. | Map inscription helpers to BRC-307. | BRC-43 is key derivation; the code comment is stale. |
| COMP-011 | Transaction README labels multicast documents with different 200-series identifiers than their filenames/titles/root summary. | Use BRC-142/143/144/148/149 and retain the mismatch as documentation evidence. | Filenames, titles, and root summary agree with each other. |
| COMP-012 | Go Script number APIs expose mutation, native-int clamping/truncation, and overflow artifacts. | Preserve consensus-visible byte and evaluation behavior, but do not reproduce caller-visible slice mutation or unsafe native-integer truncation. Each observable difference gets its own interpreter-era vector before Phase 5. | Swift value semantics and bounded conversions should improve API safety only where consensus results remain identical. |
| COMP-013 | BRC-12 now includes a network wire frame not implemented by Go v1.3.3. | Keep raw transaction encoding in the transaction model. Track the new frame as a later, versioned BSVNetwork extension. | Avoids freezing a new network frame into the lowest byte primitives before its relationship to multicast framing is settled. |
| COMP-014 | BRCs newer than Go v1.3.3 describe additional features such as STUMP and multicast. | Track them as post-parity extensions with independent feature/version identifiers. They do not silently expand a Go-parity packet. | The stated goal is complete Go SDK parity; newer BRC support remains visible without making the baseline unbounded. |
| COMP-015 | Go accepts valid SEC1 hybrid public keys (`06`/`07`), while P256K's public façade exposes compressed and uncompressed parsing. | The Swift compatibility parser accepts a hybrid key only when its prefix parity matches the encoded Y coordinate, normalizes it to ordinary uncompressed SEC1, and validates it through P256K. Public serializers emit only compressed or uncompressed forms and never hybrid. | Preserves Go input compatibility without expanding the canonical output surface. Test both valid parity prefixes, parity mismatch, wrong length, range/off-curve failures, and normalized round trips before the Phase 2 key API freezes. |
| COMP-016 | Go `chainhash.NewHashFromHex` accepts short and uppercase display strings, while the SDK's fixed-width transaction/hash value must not silently left-pad incomplete identifiers. | Swift display parsing requires exactly 64 hexadecimal characters, accepts upper- or lowercase input, and always emits lowercase. The oracle `digest32.parse` operation applies that fixed-width adapter policy before calling Go; it is not evidence that Go rejects short strings. | Exact width prevents ambiguous/incomplete transaction identifiers while case normalization remains user-friendly. Test short/long rejection, both cases, invalid characters, and display↔wire reversal. |
| COMP-017 | The initial oracle Base58Check operation composes Go SDK Base58 and SHA256d primitives rather than calling a single checked-encoding façade. | Treat the oracle operation as the Bitcoin one-byte-version Base58Check composition only. It does not establish multi-byte version policy or the public error behavior of WIF/address/extended-key Go APIs; the Phase 3 packet must compare those façades directly. | Prevents a composed test adapter from silently defining higher-level compatibility. Pin one known Base58Check value now and use format-specific Go/static vectors before public key-format APIs freeze. |
| COMP-018 | Pinned Go SDK call sites use ordinary standard Base64 decoding, which tolerates CR/LF and non-zero discarded bits; Go Base58 rejects forbidden characters but reports a non-indexed error. | Swift Hex accepts ASCII case but otherwise rejects malformed input. Swift Base64 requires canonical encoding, rejects all whitespace including CR/LF, and rejects non-zero discarded bits. Swift Base58 rejects every non-alphabet character with its zero-based UTF-8 byte offset. Every Swift text decoder requires an explicit output maximum. | Deterministic cross-platform parsing and bounded hostile-input handling outweigh permissive decoder parity. Canonical encoders remain interoperable. Test the strict Swift results against the SDK-like non-strict Base64 oracle policy, and verify that both Base58 decoders reject forbidden input while preserving their documented error-detail difference. |
| COMP-021 | Go v1.3.3 classifies a one-input transaction with a zero previous hash as coinbase when either the previous-output index or sequence is `0xffffffff`. | Require the consensus null outpoint: one input, zero previous hash, and previous-output index `0xffffffff`; sequence is irrelevant. | Avoids misclassifying an ordinary null-hash input merely because it is finalized. Test non-final coinbase sequence and zero-hash/final-sequence with a non-max index. |
| COMP-022 | Go Script ASM normalizes push encodings, returns empty text for malformed programs, and can silently ignore standalone push-opcode append errors. BRC-106, Go and @bsv/sdk 4.x give conflicting names to the Chronicle and high NOP bytes, so the same text can mean different bytes. | Treat ASM as a bounded semantic form in a named dialect. The default `.typeScript` dialect reads what @bsv/sdk 4.1.1 `fromASM` reads (its opcode names, `0`/`-1`, lowercase odd-length hex, `OP_PUSHDATA* <length> <hex>`) and writes its opcode names; where 4.1.1 `toASM` is not reversible (top-level OP_RETURN, zero-length pushes, empty input) it follows the two unmerged @bsv/sdk fixes (`OP_0` for empty pushes, a named OP_RETURN with a lenient, lossy tail, empty text as the empty script). BRC-106 names with compact BRC-14 SASM, and the Go map, remain selectable. Lowercase pushed-data hex, typed malformed/resource errors, and documented push normalization. | Raw bytes/hex remain the exact serialization. ASM written by Swift keeps its bytes in @bsv/sdk. Default ASM of a malformed OP_RETURN tail is lossy; `style: .canonical` is the strict form. Differential tests cover stable Go output; the TypeScript table is pinned against every `OP.ts` name and `Script.test.ts` vectors; Swift tests pin intentional safety differences. |
| COMP-023 | Go v1.3.3 exports `AnyOneCanPayForkID = 0xc0`, which combines two modifier bits but omits the required ALL/NONE/SINGLE base mode. | Swift signing accepts exactly `0x41`, `0x42`, `0x43`, `0xc1`, `0xc2`, and `0xc3`. The incomplete `0xc0` modifier constant is not a valid signature-hash type. | Prevents a default-to-ALL artifact from becoming an ambiguous public signing API. The oracle and Swift raw parser reject every undefined combination; all six valid combinations are differential-tested. The interpreter validates Chronicle/OTDA signatures (COMP-064); signing stays ForkID-only. |
| COMP-024 | Go's fee model uses floating-point rounding, estimates compressed P2PKH unlocks at 106 bytes although non-low-R DER can require 107, can underflow paid fees, divides by zero without change, and exposes an unimplemented random mode. | Swift uses checked integer arithmetic and a safe 107-byte P2PKH maximum, reports overspending/overflow, treats no-change excess as intentional fee, and initially exposes only equal change distribution, giving the division remainder to the last change output as @bsv/sdk does. | Preserves valid Go results for identical explicit projections while preventing rare one-byte underfunding and making hostile/incomplete states typed and nontrapping. Differential tests cover actual and projected sizes; unit tests cover overflow, dust removal, no-change, underfunding, and atomic mutation. |
| COMP-025 | Go's BRC-74 parser truncates oversized block heights, accepts unknown/combined flag bits and trailing bytes, permits zero stored levels, and its implicit root selection uses the first hash rather than a marked transaction ID. | Swift requires a UInt32 block height, nonzero height of at most 64 (BRC-74; @bsv/sdk caps at 54 for JavaScript integers, which Swift does not copy), canonical CompactSize by default, full input consumption, and bounded counts. Flags are read as the bitmask Go and @bsv/sdk use: bit 0 is a duplicate, otherwise bit 1 marks a txid, and other bits are ignored. Like @bsv/sdk, nodes above level zero must be siblings of a level-zero hash's ancestors. `root()` prefers a level-zero `txid` marker, while `root(for:)` is the unambiguous verification API. Like pinned Go, single-level compound paths derive their effective height from the largest level-zero offset, and like @bsv/sdk a single-level path pairs the right-most node of each height with itself when it has no right neighbour. `verify` returns false for a coinbase (offset 0) less than 100 blocks below the tracker's current height, as @bsv/sdk does. | Canonical paths remain byte-compatible (a duplicate's txid bit is not kept: @bsv/sdk flags 3 is written back as 1) while malformed or ambiguous inputs fail predictably instead of truncating, ignoring data, or selecting the wrong proof target. Paths @bsv/sdk writes, including flags 3 and full-block single-level paths with an odd node count, parse and prove the same root. Unit tests cover every truncation, flag bits, limits, offset zero, duplicate markers, illegal upper-level offsets, explicit targets, coinbase maturity, the @bsv/sdk valid and invalid BUMP vectors, and pinned canonical Go differentials, including effective-height root computation. |
| COMP-026 | Go's BEEF readers accept noncanonical CompactSize values, treat any nonzero v1 BUMP-presence byte as true, can panic on an invalid BUMP index, do not require full input consumption, and the generic parser silently unwraps an Atomic BEEF prefix. Its map-backed representation also does not preserve transaction wire order as a public value contract. Pinned Go v1.3.3 does not propagate validity from an unproved txid-only parent to its raw child even when `allowTxidOnly` is true, and vacuously accepts an unproved zero-input raw transaction. | Swift preserves canonical BEEF v1/v2 and Atomic BEEF bytes, requires canonical CompactSize by default, accepts only defined format bytes, bounds every outer and nested count/size, rejects trailing data and invalid proof references, preserves parent-before-child wire order, and exposes `AtomicBEEF` separately so callers cannot accidentally discard the subject. Permissive CompactSize import is explicit. Per BRC-96, transaction-ID-only records become validation anchors only when the caller opts into that trust policy; unproved zero-input raw transactions do not. Atomic validation rejects unrelated transactions and wholly unrelated BUMPs, but permits combined BUMPs to carry additional same-block leaves when the proof supports at least one relevant ancestor. | Canonical SDK envelopes remain wire-compatible while malformed or ambiguous packages fail with typed errors rather than panicking or losing framing information. The BRC-96 validation semantics take precedence over the pinned Go propagation artifact. Combined BUMPs are normal Go output and must not make an otherwise atomic ancestry graph unreadable. Independently authored exact-byte tests cover both versions and Atomic framing; a pinned persistent Go oracle covers decoding, reverse-direction emission, proof-backed validation, transaction-ID-only policy, and the recorded dependent-child divergence. Script execution and chain-tracker root trust remain separate higher-layer verification steps. |
| COMP-027 | Pinned Go `Beef.Verify` asks its chain tracker only about BUMPs containing an explicitly marked txid leaf. A structurally referenced BUMP without the optional marker can therefore make no trust call. Go's synchronous context-aware tracker interface also places concrete trackers beneath `transaction`. | Swift defines a `Sendable`, async `ChainTracker` protocol in `BSVTransaction`, keeps concrete transports in `BSVNetwork`, and computes every level-zero leaf root before verifying every supplied BUMP in deterministic block-height order. Conflicting leaf roots are malformed proof errors; a trusted tracker rejection returns `false`; tracker failures throw. `BSVSPV` exposes the proof-stage façade without claiming script execution. Like @bsv/sdk `Beef.verify`, `BEEF.verify` checks roots only and applies no coinbase maturity rule; `MerklePath.verify` and the full `SPVProofVerifier.verify(_:rootTransactionID:...)` (the counterpart of @bsv/sdk `Transaction.verify`) return `false` for a proof at offset zero until the tracker's `currentHeight()` is 100 above its block. | No supplied inclusion proof can bypass trusted-root validation because of marker metadata or a forged stored internal hash, and network clients can use native Swift concurrency without entering the transaction layer. Pinned Go differentials cover accepted/rejected roots and a conflicting two-marked-leaf BUMP; unit tests cover unmarked paths, deterministic ordering, short-circuiting, and thrown tracker failures. |
| COMP-028 | Pinned Go preserves v1 when projecting records to txid-only even though v1 cannot serialize that format. Its merge path also leaves an attached BUMP as format 00, and merging parsed txid-only duplicates can replace them with an empty raw transaction because the parser retains a nonnil placeholder object. | Swift txid-only projection always emits valid BRC-96 v2. Immutable merge promotes to v2 when required, keeps txid-only duplicates as txid-only, lets complete raw data replace placeholders, attaches merged proofs as format 01, cross-checks every BUMP leaf root, and emits stable parent-before-child order. Known-ID trimming removes only placeholders and remaps retained BUMP indexes. | These are intentional safety and validity corrections, not wire-format changes for valid envelopes. Pinned-Go semantic summaries record both merge artifacts; Swift unit and differential tests cover proof arrival, version promotion, topological ordering, projection, trimming, index remapping, and forged combined paths. |
| COMP-029 | Pinned Go `spv.Verify` accumulates each unproven transaction's input satoshis but never compares the total with its outputs; when no root fee model is supplied, an inflationary or zero-fee transaction can therefore pass the verifier. | Swift resolves every source output and requires input satoshis to be strictly greater than output satoshis for every unproven transaction, as BRC-67 specifies. An optional caller fee model can impose a stronger size-based minimum on the root transaction. Proven transactions remain chain-tracker trust anchors and are not recursively re-executed. | BRC-67 and monetary safety take precedence over the unused-variable artifact. Unit tests cover positive fee, zero fee, inflation, overflow, insufficient root policy, bad source indexes, script failure, and untrusted roots. Pinned-Go differentials cover the shared canonical path and explicitly record Go accepting the inflationary artifact that Swift rejects. |
| COMP-030 | Go BRC-42 private derivation discards the error from constructing the child scalar, and Go BRC-94 generation accepts caller-supplied `A` and `S` points without checking that they correspond to private key `a` and counterparty point `B`. Unit tests cover role agreement, exact UTF-8 invoice distinctions, malformed responses, nonce freshness, statement/proof tampering, and both proof equations. Persistent pinned-Go tests compare BRC-42 in both directions, verify a deterministic Swift proof in Go, and verify a fresh Go proof in Swift. |
| COMP-031 | Go `NewSymmetricKey` left-pads every key shorter than 32 bytes, including an empty key, retains oversized keys until AES reports an error, and `NewSymmetricKeyFromString` terminates the process on malformed Base64. | Swift accepts 1...32 input bytes, preserves the interoperable left-zero-padding rule, rejects empty and oversized keys immediately, parses only strict standard-padded Base64 with typed errors, and redacts default stringification. | COMP-033 | Pinned Go Electrum ECIES infers embedded versus omitted sender-key layout from packet length, and Bitcore compatibility derives keys from the minimal unsigned shared X coordinate while its default encryption path uses an all-zero IV. | Swift requires callers to select the Electrum embedded or omitted layout explicitly, bounds packet and ciphertext parsing, and authenticates with constant-time HMAC comparison before decryption. | COMP-034 | BRC-140, pinned Go, and TypeScript reconstruct from the first threshold shares and ignore later shares; coordinate selection accepts only a candidate resolved within five attempts. | Swift follows the same first-threshold rule after requiring common threshold and integrity fields across the supplied set, and checks duplicate x-coordinates among the shares actually used. | COMP-035 | Swift's synthesized diagnostics and reflection can expose stored secret fields even when `description` is redacted, and the initial WIF façade returned the private-key encoding from `description`. | Every public value that stores private-key, symmetric-key, mnemonic, DRBG, extended-private-key, WIF, or key-share material supplies redacted string, debug, and custom-mirror output. | COMP-036 | Pinned Go's BRC-77 parser accepts trailing ASN.1 bytes and its ECDSA verifier accepts mathematically valid high-S signatures. Unit and pinned-Go tests cover trailing data, non-minimal DER, high-S, anyone packets, and recipient-specific packets. |
| COMP-037 | Retrying a transaction POST can duplicate an accepted submission, while a provider response cannot establish which transaction the client serialized. | COMP-038 | Go wallet request structs encode zero-value artifacts: an omitted or JSON `null` counterparty means an operation-specific default, and an identity-key request may carry `protocolID: [0, ""]`. | COMP-039 | Go auto-detects Extended Format from the bytes following a transaction version, which makes a valid raw zero-input transaction whose locktime begins with the marker byte sequence ambiguous. | COMP-040 | An ARC POST can reach the provider before the client receives or validates its response. Official ARC submission success requires `status`, `title`, `timestamp`, `txid`, and `txStatus`. | COMP-041 | BRC-52 and Go use display-order revocation transaction IDs. Go also accepts or produces some values that do not satisfy one strict bounded certificate policy. JSON object keys use Unicode string equality. The Go SDK orders binary certificate fields by raw UTF-8 bytes; `@bsv/sdk` 4.1.1 writes, signs and verifies them in JavaScript `localeCompare` order (`auth/certificates/Certificate.ts:290`, `:437-458`, `:473`), so a certificate with field names such as `Zip` and `age`, `a_1` and `a1`, or `émile` and `zip` signed by one fails to verify in the other. | Swift uses display-order revocation transaction IDs, canonical Base64, canonical CompactSize, strict complete DER, low-S verification, and explicit size limits. `Certificate.binary` writes the fields in `localeCompare` order, using the ICU root collation that Node and Bun use, and `Certificate.signed` and `CertificateEngine.issue` sign that binary. `LocaleCompareOrder` (BSVCore) reproduces the collation exactly for printable ASCII and for the 488 precomposed Latin letters in U+00C0-U+024F and U+1E00-U+1EFF that decompose to an ASCII letter and combining diacritics, such as `é`, `Å` and `ǖ`. `Certificate.signed` and `CertificateEngine.issue` refuse any other field name with `CertificateFieldNameError.unsupportedCharacter`, because ICU orders other scripts, letters such as `ø` and `ß`, and decomposed accents in ways this SDK does not reproduce, and ignores control characters, so the order TypeScript verifies could not be predicted. `Certificate.verifySignature`, BRC-103 exchange, `CertificateEngine` and `IdentityClient.publiclyRevealAttributes` accept a signature over the `localeCompare` order or over the UTF-8 byte order. `Certificate(binary:)` reads fields in any order with no repeated name (COMP-048). The caller must check the revocation output before it trusts a certificate. | Canonical values stay interoperable with both SDKs; certificates Swift issues verify in TypeScript, TypeScript certificate binary re-encodes byte for byte, and Go and earlier Swift certificates still verify. Go verifies Swift certificates only when `localeCompare` and byte order agree on their names. Strict parsing prevents ambiguous fields, trailing data, hidden signature bytes, and lossy JSON conversion. Tests cover binary and JSON boundaries, Unicode-equivalent names, the order against Bun and Node for all printable ASCII pairs and for the accented Latin letters, TypeScript-signed certificates with mixed-case, accented, underscored and numbered names, both signature orders, signature binding, field encryption, verifier projection, all-or-nothing failure, secret redaction, and refusal of unsupported names. Certificates with other non-ASCII names signed elsewhere are verified in both orders this SDK knows and can fail to verify, and TypeScript hosts with a non-English default locale may order names differently. |

Swift emits the BRC-307 enriched `OP_RETURN` suffix and rejects invalid input indexes, satoshi ranges, missing source data, and arithmetic overflow before transaction mutation. | The Swift rules preserve canonical protocol output and prevent ambiguous text or partial transaction changes. Tests cover every size boundary, checksum, prefix deviation, push boundary, ordinal boundary, atomic failure, and pinned-Go canonical BIP-276 behavior. |

## Scope decisions

- BRC-140 key shares/backups are accepted in the cryptographic-primitives phase;
  they were not required before byte, hashing, and key parsing foundations.
- `BSVWallet` now covers the accepted offline BRC-100 value types, capability
  protocols, key derivation, ProtoWallet behavior, and serializers. Substrates,
  permission policy, and persistent end-user wallet state remain later work.
- Full BASM, STUMP, multicast, overlay-node hosting, payment families, token
  engines, and application schemas remain cataloged but do not gate the first
  primitive waves unless a Go parity dependency requires them.
