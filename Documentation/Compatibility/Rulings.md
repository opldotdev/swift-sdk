# Compatibility rulings

Status: Approved for implementation after the detailed Fable readiness review.

The default precedence is network consensus and applicable BRC requirements,
then accepted cross-SDK vectors, then incidental Go SDK behavior. When one BRC
document contradicts its own vectors, a newer governing BRC, or an established
wire implementation, the exact exception is recorded here rather than hidden
behind the general rule.

| ID | Conflict | Proposed Swift behavior | Reason and test obligation |
| --- | --- | --- | --- |
| COMP-001 | CompactSize decoding in Go accepts non-minimal forms and some callers use max-u64 as “-1”. | Provide bounded permissive and canonical-required decoding policies. Encode canonically. Model max-u64 absence as a named sentinel only in formats that specify it; never as an ordinary length. | Preserves wire import compatibility without allowing ambiguous canonical output or unbounded allocation. Test every prefix boundary, truncation, non-minimal form, max-u64, and per-call maximum. |
| COMP-002 | BRC-2 prose describes a shared-secret hash input that disagrees with the published vectors and Go. | Follow the published vectors and Go v1.3.3 padded-x-coordinate derivation. Mark the prose conflict and do not offer a second silent variant. | The vectors are interoperable evidence. Test exact ciphertext, plaintext, HMAC, wrong counterparty/protocol/key ID, tag tampering, and IV/tag truncation. |
| COMP-003 | BRC-30 says four-byte source satoshis; Go and Bitcoin amounts use eight bytes. | Parse and emit unsigned 64-bit little-endian source amounts. Do not emit the ambiguous four-byte form. | Matches Go Extended Format and the transaction amount domain. Test Go↔Swift bytes and overflow/truncation. |
| COMP-004 | BRC-43 gives 280/1033 limits; BRC-100 and Go use 400/800. Go's Unicode-aware trimming and lowercasing can also admit names outside a stable ASCII derivation profile. | Use protocol names of 5…400 UTF-8 bytes and key IDs of 1…800 UTF-8 bytes. Protocol names trim ASCII whitespace, lowercase ASCII, allow only letters, digits, and single spaces, reject the `admin` prefix and ` protocol` suffix, and do not normalize key IDs. | Newer wallet limits and the parity baseline agree. The stricter Swift identifier policy fails closed rather than deriving a different key from Unicode or reserved-name artifacts. Tests cover byte boundaries, every ASCII character, Unicode rejection, reserved names, and distinct composed/decomposed key IDs. |
| COMP-005 | BRC-48 specifies lock-after PushDrop; Go creates both but decodes only lock-before. | Decode and construct spec-conformant lock-after. Support lock-before through an explicitly named compatibility mode. | Achieves BRC conformance without losing Go ecosystem inputs. Test that no auto-detection ambiguity changes pushed data. |
| COMP-006 | BRC-74 pseudocode can be read as rejecting offset zero. | Accept offset/index zero. | The binary model and Go behavior require zero. Use independently authored zero-index cases and the pinned external oracle; do not copy the Open BSV example into the MIT fixture bundle under the current license policy. |
| COMP-007 | A Go comment associates BEEF v1 with BRC-64. | Treat BRC-62 as authoritative for BEEF v1. | The comment is non-functional and contradicts the specification registry. |
| COMP-008 | BRC-78’s table/value and Go use `42421033`; one example reverses it. | Use `42421033` on the wire. | Table plus implementation outweigh the isolated example. Keep a regression case documenting the source discrepancy. |
| COMP-009 | BRC-103/Go authentication version `0.1` conflicts with BRC-104 material showing `1.0`. | Defer emission policy to a BSVAuth version-negotiation ADR. Parsers must reject unknown versions and tests must separately cover accepted profiles; no silent normalization. | This does not affect primitive APIs and should not be guessed before the auth transport design. |
| COMP-010 | Go inscription comments call ordinals BRC-43. | Map inscription helpers to BRC-307. | BRC-43 is key derivation; the code comment is stale. |
| COMP-011 | Transaction README labels multicast documents with different 200-series identifiers than their filenames/titles/root summary. | Use BRC-142/143/144/148/149 and retain the mismatch as documentation evidence. | Filenames, titles, and root summary agree with each other. |
| COMP-012 | Go Script number APIs expose mutation, native-int clamping/truncation, and overflow artifacts. | Preserve consensus-visible byte and evaluation behavior, but do not reproduce caller-visible slice mutation or unsafe native-integer truncation. Each observable difference gets its own interpreter-era vector before Phase 5. | Swift value semantics and bounded conversions should improve API safety only where consensus results remain identical. |
| COMP-013 | BRC-12 now includes a network wire frame not implemented by Go v1.3.3. | Keep raw transaction encoding in the transaction model. Track the new frame as a later, versioned BSVNetwork extension. | Avoids freezing a new network frame into the lowest byte primitives before its relationship to multicast framing is settled. |
| COMP-014 | BRCs newer than Go v1.3.3 describe additional features such as STUMP and multicast. | Track them as post-parity extensions with independent feature/version identifiers. They do not silently expand a Go-parity packet. | The stated goal is complete Go SDK parity; newer BRC support remains visible without making the baseline unbounded. |
| COMP-015 | Go accepts valid SEC1 hybrid public keys (`06`/`07`), while P256K's public façade exposes compressed and uncompressed parsing. | The Swift compatibility parser accepts a hybrid key only when its prefix parity matches the encoded Y coordinate, normalizes it to ordinary uncompressed SEC1, and validates it through P256K. Public serializers emit only compressed or uncompressed forms and never hybrid. | Preserves Go input compatibility without expanding the canonical output surface. Test both valid parity prefixes, parity mismatch, wrong length, range/off-curve failures, and normalized round trips before the Phase 2 key API freezes. |
| COMP-016 | Go `chainhash.NewHashFromHex` accepts short and uppercase display strings, while the SDK's fixed-width transaction/hash value must not silently left-pad incomplete identifiers. | Swift display parsing requires exactly 64 hexadecimal characters, accepts upper- or lowercase input, and always emits lowercase. The oracle `digest32.parse` operation applies that fixed-width adapter policy before calling Go; it is not evidence that Go rejects short strings. | Exact width prevents ambiguous/incomplete transaction identifiers while case normalization remains user-friendly. Test short/long rejection, both cases, invalid characters, and display↔wire reversal. |
| COMP-017 | The initial oracle Base58Check operation composes Go SDK Base58 and SHA256d primitives rather than calling a single checked-encoding façade. | Treat the oracle operation as the Bitcoin one-byte-version Base58Check composition only. It does not establish multi-byte version policy or the public error behavior of WIF/address/extended-key Go APIs; the Phase 3 packet must compare those façades directly. | Prevents a composed test adapter from silently defining higher-level compatibility. Pin one known Base58Check value now and use format-specific Go/static vectors before public key-format APIs freeze. |
| COMP-018 | Pinned Go SDK call sites use ordinary standard Base64 decoding, which tolerates CR/LF and non-zero discarded bits; Go Base58 rejects forbidden characters but reports a non-indexed error. | Swift Hex accepts ASCII case but otherwise rejects malformed input. Swift Base64 requires canonical encoding, rejects all whitespace including CR/LF, and rejects non-zero discarded bits. Swift Base58 rejects every non-alphabet character with its zero-based UTF-8 byte offset. Every Swift text decoder requires an explicit output maximum. | Deterministic cross-platform parsing and bounded hostile-input handling outweigh permissive decoder parity. Canonical encoders remain interoperable. Test the strict Swift results against the SDK-like non-strict Base64 oracle policy, and verify that both Base58 decoders reject forbidden input while preserving their documented error-detail difference. |
| COMP-021 | Go v1.3.3 classifies a one-input transaction with a zero previous hash as coinbase when either the previous-output index or sequence is `0xffffffff`. | Require the consensus null outpoint: one input, zero previous hash, and previous-output index `0xffffffff`; sequence is irrelevant. | Avoids misclassifying an ordinary null-hash input merely because it is finalized. Test non-final coinbase sequence and zero-hash/final-sequence with a non-max index. |
| COMP-022 | Go Script ASM normalizes push encodings, returns empty text for malformed programs, and can silently ignore standalone push-opcode append errors. | Treat ASM as a bounded semantic form: canonical BRC-106 names, compact BRC-14 SASM, lowercase pushed-data hex, typed malformed/resource errors, and documented push normalization. | Raw bytes/hex remain the exact serialization. Differential tests cover stable Go output; Swift tests pin intentional safety differences. |
| COMP-023 | Go v1.3.3 exports `AnyOneCanPayForkID = 0xc0`, which combines two modifier bits but omits the required ALL/NONE/SINGLE base mode. | Swift signing accepts exactly `0x41`, `0x42`, `0x43`, `0xc1`, `0xc2`, and `0xc3`. The incomplete `0xc0` modifier constant is not a valid signature-hash type. | Prevents a default-to-ALL artifact from becoming an ambiguous public signing API. The oracle and Swift raw parser reject every undefined combination; all six valid combinations are differential-tested. |
| COMP-024 | Go's fee model uses floating-point rounding, estimates compressed P2PKH unlocks at 106 bytes although non-low-R DER can require 107, can underflow paid fees, divides by zero without change, and exposes an unimplemented random mode. | Swift uses checked integer arithmetic and a safe 107-byte P2PKH maximum, reports overspending/overflow, treats no-change excess as intentional fee, and initially exposes only equal change distribution. | Preserves valid Go results for identical explicit projections while preventing rare one-byte underfunding and making hostile/incomplete states typed and nontrapping. Differential tests cover actual and projected sizes; unit tests cover overflow, dust removal, no-change, underfunding, and atomic mutation. |
| COMP-025 | Go's BRC-74 parser truncates oversized block heights, accepts unknown/combined flag bits and trailing bytes, permits zero stored levels, and its implicit root selection uses the first hash rather than a marked transaction ID. | Swift requires a UInt32 block height, nonzero height of at most 64, exact flags 0/1/2, canonical CompactSize by default, full input consumption, and bounded counts. `root()` prefers a level-zero `txid` marker, while `root(for:)` is the unambiguous verification API. Like pinned Go, single-level compound paths derive their effective height from the largest level-zero offset. | Canonical paths remain byte-compatible while malformed or ambiguous inputs fail predictably instead of truncating, ignoring data, or selecting the wrong proof target. Unit tests cover every truncation, invalid flags, limits, offset zero, duplicate markers, explicit targets, and pinned canonical Go differentials, including effective-height root computation. |
| COMP-026 | Go's BEEF readers accept noncanonical CompactSize values, treat any nonzero v1 BUMP-presence byte as true, can panic on an invalid BUMP index, do not require full input consumption, and the generic parser silently unwraps an Atomic BEEF prefix. Its map-backed representation also does not preserve transaction wire order as a public value contract. Pinned Go v1.3.3 does not propagate validity from an unproved txid-only parent to its raw child even when `allowTxidOnly` is true, and vacuously accepts an unproved zero-input raw transaction. | Swift preserves canonical BEEF v1/v2 and Atomic BEEF bytes, requires canonical CompactSize by default, accepts only defined format bytes, bounds every outer and nested count/size, rejects trailing data and invalid proof references, preserves parent-before-child wire order, and exposes `AtomicBEEF` separately so callers cannot accidentally discard the subject. Permissive CompactSize import is explicit. Per BRC-96, transaction-ID-only records become validation anchors only when the caller opts into that trust policy; unproved zero-input raw transactions do not. Atomic validation rejects unrelated transactions and wholly unrelated BUMPs, but permits combined BUMPs to carry additional same-block leaves when the proof supports at least one relevant ancestor. | Canonical SDK envelopes remain wire-compatible while malformed or ambiguous packages fail with typed errors rather than panicking or losing framing information. The BRC-96 validation semantics take precedence over the pinned Go propagation artifact. Combined BUMPs are normal Go output and must not make an otherwise atomic ancestry graph unreadable. Independently authored exact-byte tests cover both versions and Atomic framing; a pinned persistent Go oracle covers decoding, reverse-direction emission, proof-backed validation, transaction-ID-only policy, and the recorded dependent-child divergence. Script execution and chain-tracker root trust remain separate higher-layer verification steps. |
| COMP-027 | Pinned Go `Beef.Verify` asks its chain tracker only about BUMPs containing an explicitly marked txid leaf. A structurally referenced BUMP without the optional marker can therefore make no trust call. Go's synchronous context-aware tracker interface also places concrete trackers beneath `transaction`. | Swift defines a `Sendable`, async `ChainTracker` protocol in `BSVTransaction`, keeps concrete transports in `BSVNetwork`, and computes every level-zero leaf root before verifying every supplied BUMP in deterministic block-height order. Conflicting leaf roots are malformed proof errors; a trusted tracker rejection returns `false`; tracker failures throw. `BSVSPV` exposes the proof-stage façade without claiming script execution. | No supplied inclusion proof can bypass trusted-root validation because of marker metadata or a forged stored internal hash, and network clients can use native Swift concurrency without entering the transaction layer. Pinned Go differentials cover accepted/rejected roots and a conflicting two-marked-leaf BUMP; unit tests cover unmarked paths, deterministic ordering, short-circuiting, and thrown tracker failures. |
| COMP-028 | Pinned Go preserves v1 when projecting records to txid-only even though v1 cannot serialize that format. Its merge path also leaves an attached BUMP as format 00, and merging parsed txid-only duplicates can replace them with an empty raw transaction because the parser retains a nonnil placeholder object. | Swift txid-only projection always emits valid BRC-96 v2. Immutable merge promotes to v2 when required, keeps txid-only duplicates as txid-only, lets complete raw data replace placeholders, attaches merged proofs as format 01, cross-checks every BUMP leaf root, and emits stable parent-before-child order. Known-ID trimming removes only placeholders and remaps retained BUMP indexes. | These are intentional safety and validity corrections, not wire-format changes for valid envelopes. Pinned-Go semantic summaries record both merge artifacts; Swift unit and differential tests cover proof arrival, version promotion, topological ordering, projection, trimming, index remapping, and forged combined paths. |
| COMP-029 | Pinned Go `spv.Verify` accumulates each unproven transaction's input satoshis but never compares the total with its outputs; when no root fee model is supplied, an inflationary or zero-fee transaction can therefore pass the verifier. | Swift resolves every source output and requires input satoshis to be strictly greater than output satoshis for every unproven transaction, as BRC-67 specifies. An optional caller fee model can impose a stronger size-based minimum on the root transaction. Proven transactions remain chain-tracker trust anchors and are not recursively re-executed. | BRC-67 and monetary safety take precedence over the unused-variable artifact. Unit tests cover positive fee, zero fee, inflation, overflow, insufficient root policy, bad source indexes, script failure, and untrusted roots. Pinned-Go differentials cover the shared canonical path and explicitly record Go accepting the inflationary artifact that Swift rejects. |
| COMP-030 | Go BRC-42 private derivation discards the error from constructing the child scalar, and Go BRC-94 generation accepts caller-supplied `A` and `S` points without checking that they correspond to private key `a` and counterparty point `B`. Its proof value also permits an arbitrary `big.Int` response until verification. | Swift BRC-42 throws a typed error if the derived scalar is zero. Swift BRC-94 generation accepts only the prover private key and counterparty public key, derives `A` and `S` internally, generates its nonce through P256K/libsecp256k1, and admits only exact 32-byte nonzero responses below the curve order. Verification is nontrapping and returns `false` for failed equations. | Valid wire proofs and child keys remain exactly compatible while structurally inconsistent statements and scalar artifacts are unrepresentable. Unit tests cover role agreement, exact UTF-8 invoice distinctions, malformed responses, nonce freshness, statement/proof tampering, and both proof equations. Persistent pinned-Go tests compare BRC-42 in both directions, verify a deterministic Swift proof in Go, and verify a fresh Go proof in Swift. |
| COMP-031 | Go `NewSymmetricKey` left-pads every key shorter than 32 bytes, including an empty key, retains oversized keys until AES reports an error, and `NewSymmetricKeyFromString` terminates the process on malformed Base64. | Swift accepts 1...32 input bytes, preserves the interoperable left-zero-padding rule, rejects empty and oversized keys immediately, parses only strict standard-padded Base64 with typed errors, and redacts default stringification. Encryption delegates to Swift Crypto AES-GCM with a fresh 32-byte nonce and emits the exact Go `nonce || ciphertext || 16-byte tag` envelope without AAD. | Empty all-zero keys and process termination are unsafe construction artifacts, not required wire behavior. Unit tests cover every relevant key length, malformed Base64, randomness, empty plaintext, truncation, and tampering. Persistent pinned-Go tests compare deterministic envelopes and decrypt in both directions, including 31-byte coordinate-style keys. |
| COMP-032 | The legacy Bitcoin Signed Message wire format defines compact headers `27...34`, while Go's address-verification helper derives a mainnet address regardless of the caller's intended network. | Swift accepts only headers `27...34`, preserves their recovery and compression bits, and verifies the recovered key against a supplied `LegacyAddress` on that address's network. | The signature wire format is network-neutral; address encoding is not. Tests cover all eight valid headers, adjacent invalid values, mainnet and testnet verification, bitcoinj vectors, and bidirectional pinned-Go signing and recovery. |
| COMP-033 | Pinned Go Electrum ECIES infers embedded versus omitted sender-key layout from packet length, and Bitcore compatibility derives keys from the minimal unsigned shared X coordinate while its default encryption path uses an all-zero IV. | Swift requires callers to select the Electrum embedded or omitted layout explicitly, bounds packet and ciphertext parsing, and authenticates with constant-time HMAC comparison before decryption. The ordinary encryption APIs always generate a fresh ephemeral sender key. Deterministic caller-supplied sender keys and Bitcore IVs are exposed only through explicitly named `encryptCompatibility` seams that warn against reuse. | Explicit layouts avoid ambiguous length heuristics without changing valid packets, while the obvious encryption path is safe against accidental key reuse. Unit and pinned-Go differential tests cover both Electrum layouts, Bitcore minimal-X derivation, zero- and explicit-IV envelopes, truncation, malformed keys, bad block lengths, and authentication failures. |
| COMP-034 | BRC-140 and pinned Go perform secret sharing with variable-time big-integer interpolation over the secp256k1 field prime, and recovery can otherwise ignore shares beyond the threshold. | Swift uses the BRC-140 field prime, accepts only canonical bounded share text, caps splitting and recovery at 20 shares, and validates every extra share against the threshold-sized interpolation basis. Secret-bearing text is available only through the explicit `backupString` export; normal and debug descriptions are redacted. | Variable-time interpolation is limited to offline backup workflows and is not presented as safe for attacker-observable online use. Tests cover canonical round trips, configuration and CPU bounds, malformed or inconsistent shares, extra-share validation, integrity checks, and redaction. |
| COMP-035 | Swift's synthesized diagnostics and reflection can expose stored secret fields even when `description` is redacted, and the initial WIF façade returned the private-key encoding from `description`. | Every public value that stores private-key, symmetric-key, mnemonic, DRBG, extended-private-key, WIF, or key-share material supplies redacted string, debug, and custom-mirror output. Secret serialization remains available only through explicitly named exports such as `bytes`, `phrase`, `serialized`, `encoded`, and `backupString`. | Ordinary interpolation, `dump`, `Mirror`, debugger diagnostics, and logging must not become accidental key-export APIs. Tests capture each diagnostic path, require an empty custom mirror, and prove known secret fragments are absent while explicit exports retain exact wire compatibility. |
| COMP-036 | Pinned Go's BRC-77 parser accepts trailing ASN.1 bytes and its ECDSA verifier accepts mathematically valid high-S signatures. The anyone recipient is encoded by one zero discriminator and uses the protocol's scalar-one derivation key. | Swift requires one complete, canonical strict-DER signature. A canonical high-S signature remains parseable but verification returns `false`; signatures created by either SDK are low-S. Anyone mode consumes exactly one zero byte and ignores any supplied recipient private key. | Canonical packets remain bidirectionally compatible while parser ambiguity and the existing strict ECDSA policy stay visible. Unit and pinned-Go tests cover trailing data, non-minimal DER, high-S, anyone packets, and recipient-specific packets. |
| COMP-037 | Retrying a transaction POST can duplicate an accepted submission, while a provider response cannot establish which transaction the client serialized. Cancellation or transport failure after a POST starts does not prove that the provider rejected it. | WhatsOnChain chain-tracker GETs retry only bounded transient failures and honor a capped `Retry-After`. Broadcast POSTs are never retried, even under a policy with additional attempts. Swift computes the transaction ID locally, requires one canonical lowercase provider ID that matches it, rejects redirects and oversized responses, and redacts transaction material from error excerpts. | Read retries remain bounded and broadcast side effects are not duplicated automatically. Broadcast failure after dispatch is reported as failure with uncertain delivery; callers must reconcile the transaction ID before resubmitting. Tests cover retry classes and bounds, cancellation, strict responses, ID mismatch, redaction, and exactly one POST. |
| COMP-038 | Go wallet request structs encode zero-value artifacts: an omitted or JSON `null` counterparty means an operation-specific default, and an identity-key request may carry `protocolID: [0, ""]`. Treating every `null` as absence would also hide malformed known fields. | Swift accepts missing or `null` counterparty only at the flattened request field and maps it to that operation's `.self` or `.anyone` default. It accepts the exact zero protocol tuple only with `identityKey: true` and no contradictory fields. Canonical output emits the explicit counterparty or only `identityKey: true`; `null` for other known fields is rejected. | This imports Go-generated requests without making the typed JSON model broadly nullable or preserving meaningless zero fields. Tests cover each operation's default, canonical re-encoding, the exact identity artifact, contradictions, and rejected known-field nulls. |
| COMP-039 | Go auto-detects Extended Format from the bytes following a transaction version, which makes a valid raw zero-input transaction whose locktime begins with the marker byte sequence ambiguous. BRC-128 prose also shows one extra zero while its table and Go use the six-byte `00 00 00 00 00 EF` marker. | Swift requires callers to select `.raw` or `.extended`, emits and accepts the six-byte marker, and never auto-detects. Extended source amounts remain the eight-byte values selected by COMP-003. | Explicit selection preserves every raw transaction byte string and transaction ID while retaining canonical Go-compatible Extended Format. Tests cover the raw collision, literal marker mismatch/truncation, eight-byte amounts, canonical and permissive CompactSize policies, and bidirectional pinned-Go encoding. |
| COMP-040 | An ARC POST can reach the provider before the client receives or validates its response. Official ARC submission success requires `status`, `title`, `timestamp`, `txid`, and `txStatus`. Status lookup success requires `timestamp`, `txid`, and `txStatus`, but it does not require `status` or `title`. A redirect, oversized response, malformed semantic field, or wrong transaction ID does not prove rejection. | Swift never retries an ARC POST. It validates operation-specific fields without removing control or format characters from semantic values. It returns explicit rejection only for a valid matching ARC rejection or a documented ARC validation status. Every other response failure after POST begins returns `uncertainDelivery` with the local transaction ID and a typed cause. | This prevents unsafe automatic resubmission and prevents malformed text from becoming a valid status or proof field. Tests cover preflight failure with zero POSTs, cancellation, timeout, transport loss, redirects, response limits, malformed responses, wrong transaction IDs, official response shapes, semantic-field injection, and explicit rejection. |
| COMP-041 | BRC-52 and Go use display-order revocation transaction IDs. Go also accepts or produces some values that do not satisfy one strict bounded certificate policy. JSON object keys use Unicode string equality, while the binary certificate orders field names by raw UTF-8 bytes. | Swift uses display-order revocation transaction IDs, canonical Base64, canonical CompactSize, strict complete DER, low-S verification, raw UTF-8 field-name order, and explicit size limits. It rejects byte-distinct field names that are canonically equivalent in Unicode so JSON output cannot silently replace a signed field. Certificate verification is cryptographic only. The caller must check the revocation output before it trusts a certificate. | Canonical values stay interoperable. Strict parsing prevents ambiguous fields, trailing data, hidden signature bytes, and lossy JSON conversion. Tests cover binary and JSON boundaries, Unicode-equivalent names, field order, signature binding, field encryption, verifier projection, all-or-nothing failure, and secret redaction. |
| COMP-042 | Go BIP-276 accepts a broader prefix domain and re-encodes parsed values before checksum comparison. Its BRC-307 enriched-inscription path omits the enriched suffix, and its specific-ordinal helper has unsafe range artifacts. | Swift emits and requires canonical lowercase BIP-276 text with a restricted lowercase prefix. Swift emits the BRC-307 enriched `OP_RETURN` suffix and rejects invalid input indexes, satoshi ranges, missing source data, and arithmetic overflow before transaction mutation. | The Swift rules preserve canonical protocol output and prevent ambiguous text or partial transaction changes. Tests cover every size boundary, checksum, prefix deviation, push boundary, ordinal boundary, atomic failure, and pinned-Go canonical BIP-276 behavior. |

## Scope decisions

- BRC-140 key shares/backups are accepted in the cryptographic-primitives phase;
  they were not required before byte, hashing, and key parsing foundations.
- `BSVWallet` now covers the accepted offline BRC-100 value types, capability
  protocols, key derivation, ProtoWallet behavior, and serializers. Substrates,
  permission policy, and persistent end-user wallet state remain later work.
- Full BASM, STUMP, multicast, overlay-node hosting, payment families, token
  engines, and application schemas remain cataloged but do not gate the first
  primitive waves unless a Go parity dependency requires them.
