## Scope and baselines

- BRC corpus: `/Users/satchmo/code/BRCs`, Git commit `a0b5e42c01f13a1506b063a83070e81d4090debb` (working tree clean when audited).
- Go reference: clean extracted source `/private/tmp/bsv-go-sdk-research`, pinned by the project to `bsv-blockchain/go-sdk` v1.3.3 / commit `de26fdec57a945ddc06de5d5617f6c32374f3929`. - “Full/partial/none” below means implemented in the pinned Go source, not necessarily production-complete or conformant to every newly edited sentence in the local BRC corpus.
- This is a functional/provenance audit, not a legal opinion.

## Executive findings

1. The direct Phase 0/1 conformance spine should be BRC-12, 14, 16, 42, 43/44, 2, 3, 30, 62, 67, 74, 95, and 96. BRC-106 should gate public ASM round trips. BRC-36 should gate outpoint identity first, with its richer portable object deferred unless needed by the wallet surface.
2. BRC-74 is the current unified Merkle-path format. BRC-58, 61, and 71 are historical inputs/compatibility formats. BRC-119 STUMP is a distinct subtree proof that composes into BUMP and is absent from Go v1.3.3.
3. BRC-62/96/95 define the BEEF lineage (v1, v2, Atomic BEEF). BRC-8 Everett envelopes and the older BRC-9/10/11 proof path must not drive the new primitive API.
4. BRC-100 is the current wallet interface and subsumes the old BRC-1 through BRC-7 action/wallet framing. BRC-116 is the authoritative current permission lifecycle; BRC-73 and BRC-98/99/111/112/114 are compatible extensions. Go exposes much of the BRC-100 ABI/types but is not a persistent wallet or full permission UI implementation.
5. BRC-52 expressly makes itself the authoritative certificate primitive for BRC-100/103/104. The Authrite-era BRC-31, 53, and 56 are historical context, not the normative certificate model.
6. Local BRC edits are newer than Go v1.3.3 and contain observable contradictions: EF source satoshis 4 vs Go’s 8 bytes; BRC-2 shared-secret prose vs passing vectors; BRC-43 limits vs BRC-100/Go limits; BRC-78 magic byte order; BRC-103/104 auth version; and incorrect transaction README identifiers. These need explicit compatibility decisions, not silent interpretation.

## Recommended Phase 0 and Phase 1 gates

### Phase 0: deterministic primitives and value types

The following BRC behavior should directly gate public primitive APIs:

1. **Bytes and transaction identity — BRC-12:** strict CompactSize, LE integer codecs, hash byte-order types, raw transaction round trips and txid. Keep the new BRC-12 network frame behind a separate API/feature until its relation to multicast framing is settled.
2. **Scripts — BRC-14 and BRC-106:** lossless binary/hex, chunk parsing, canonical ASM output and permissive documented aliases. Add BRC-16 P2PKH/address as the first template. Full BRC-15 BASM is explicitly not a Phase 0 gate.
3. **Keys — BRC-42:** require every published private/public derivation vector and invalid-tweak tests. Make BRC-43 protocol/keyID/counterparty typed values shared across APIs; select the Go/BRC-100 400/800 limit profile explicitly and enforce BRC-44’s `admin` reservation at the wallet boundary.
4. **Wallet crypto primitives — BRC-2 and BRC-3:** exact decrypt/HMAC verification vectors, AES-GCM layout and DER verification. For BRC-2, use vector/Go behavior until the shared-point prose conflict is resolved.
5. **Outpoints — BRC-36 identity portion:** txid+vout binary and canonical string. Defer basket/export/portable Atomic-BEEF object unless the Phase 0 API promises wallet interchange.
6. **Merkle proofs — BRC-74:** binary/JSON round trip, root computation, verification, merge, duplicate markers, index zero, overflow/truncation/malformed-height tests.
7. **Optional key backup — BRC-140:** only if backup/share APIs are exposed in Phase 0; otherwise defer wholesale. If included, gate field-p behavior, fixed-seed derivation using Go’s 4-byte-BE counter convention, recovery, integrity and malformed-share rejection.

Non-BRC foundations must also gate Phase 0: SEC1 compressed/uncompressed secp256k1 parsing, scalar/point validation, ECDSA DER and sighash semantics, SHA-1/256/512/SHA256d, RIPEMD160/HASH160, HMAC, AES-GCM, Base58Check, ScriptNum/minimal push rules, and secure randomness. BRC conformance cannot substitute for those consensus/cryptographic sources.

### Phase 1: complete transactions, proofs, and portable messages

1. **Extended transactions — BRC-30:** parse/serialize EF and use the Go/de-facto 8-byte source amount, with the prose discrepancy documented and tested.
2. **BEEF lineage — BRC-62, 96, 95:** exact v1/v2/Atomic vectors; strict topology; bump indexes; txid-only resolution; subject-only ancestry; duplicate/conflict rejection.
3. **SPV — BRC-67 + BRC-74:** source-output resolution, input/output/fee accounting, script validation, locktime/sequence, BUMP root verification through an injected chain tracker. Use trust-policy interfaces rather than embedding one vendor service.
4. **Common scripts — BRC-18/19/47/48:** include only those promised by the Phase 1 surface. If PushDrop is public, fix the Go mismatch by supporting the spec’s lock-after decode and treating lock-before as an explicitly named compatibility extension.
5. **Portable messages — BRC-77/78:** exact wire vectors and negative/truncation tests. Select `42421033` for BRC-78 Go parity and file an erratum against the reversed example.
6. **BRC-100 serializer:** may begin in Phase 1 after the above types stabilize, but should be described as ABI/wire support until persistence, permissions, certificates and transports exist. Certificate/auth protocol behavior (BRC-52/103/104) is a subsequent `BSVAuth` gate unless the roadmap explicitly puts auth in Phase 1.

Not Phase 0/1 gates: BRC-15 full assembler, STUMP and multicast BRC-119/124–149, wallet permission UI/lifecycle, backup services/discovery, full overlay nodes, HTTP payment families, token/application protocols, and opinion documents.

## Required cross-language conformance corpus

- BRC-42: all ten published child-key vectors (five private, five public), both matching and mismatched sender/recipient perspectives.
- BRC-2: exact published ciphertext/plaintext and HMAC vectors; add tampered tag, wrong protocol/keyID/counterparty, and truncated IV/tag cases.
- BRC-3: published signature verification cases plus malformed DER/high-S policy tests according to the selected consensus policy; avoid signature-byte equality unless nonce strategy is normative.
- BRC-12/30: Go-produced raw/EF bytes decoded by Swift and Swift-produced bytes decoded by Go; boundary CompactSize values and max-u64 sentinel.
- BRC-74: exact published hex/root/txids, index zero, duplicate nodes, merge success, unequal-height/root rejection, malformed flags/levels.
- BRC-62/96/95: exact BRC/Go fixtures plus invalid graph ordering, unresolved txid-only references, unrelated Atomic-BEEF transactions, invalid bump indexes.
- BRC-77/78: exact serialized messages and malformed/truncated/adversarial input cases; BRC-78 locks the selected magic order.
- BRC-140 if exposed: fixed seeded shares matching Go’s BE counter construction, reconstruction with every threshold-sized subset, invalid integrity and duplicate-x rejection.
- For every codec: canonical encoding tests, permissive-decoding policy tests, integer overflow/allocation caps, trailing-byte policy, and fuzz/property round trips.

## Licensing and provenance observations

- The audited BRC checkout identifies an upstream GitHub repository and commit, but no repository-level `LICENSE`, `COPYING`, or `NOTICE` file was present at depth ≤2.
- Some individual documents contain their own statement that the specification is licensed under the Open BSV License (examples include BRC-30, 61, 62, 71, 74, and 119). Many others do not state a document-level license in their text.
- Several documents are summaries or links to externally maintained standards rather than self-contained grants/copies: notably BRC-10/TSC Merkle proof, BRC-32/BIP-32, BRC-75/BIP-39, and BRC-120’s frozen external x402 v1 dependency. Their normative text, test-vector provenance, and licenses must be recorded separately.
- The repository README presents the documents as evolving proposals and directs substantial revisions toward new standards; newer normative BRCs can therefore supersede historical context. A commit lock is essential for reproducible conformance.
- These facts do not determine whether any particular implementation, excerpt, vector, or vendored asset is legally usable. Practical engineering posture: keep a per-fixture source/commit record; write independent test harness code; avoid copying substantial prose or externally sourced wordlists/vectors into the SDK without confirming their provenance; and have the project owner perform the intended license review.

## Decisions needed before freezing Swift public APIs

1. Adopt “Go v1.3.3 parity with documented BRC exceptions” as the rule, or prefer latest local BRC prose when it contradicts Go. A single global rule is insufficient unless the exceptions above are resolved individually.
2. Confirm whether BRC-12’s newly added wire frame is in Phase 1 or a future `BSVNetwork` feature.
3. Select BRC-43 length profile (recommended for parity: BRC-100/Go 400/800) and decide whether non-ASCII length is counted in Swift characters, Unicode scalars, or UTF-8 bytes; the documents use inconsistent nouns.
4. Confirm EF source amount as 8-byte LE and publish an interoperability note.
5. Select BRC-78 magic and BRC-103/104 version emission/acceptance rules.
6. Decide whether `BSVWallet` Phase 1 promises only BRC-100 value types/serializer, or a stateful wallet. The latter expands scope to permission, basket, action, certificate, backup and synchronization semantics.
7. Decide whether BRC-140 is core key custody or later wallet backup; its deterministic internal counter layout must be frozen if public.
8. Establish an extension namespace/versioning policy for specs newer than Go v1.3.3 (especially BRC-153), so parity and latest-BRC support remain distinguishable.

## Bottom line

Build Phase 0 around strict Bitcoin primitives plus BRC-12/14/16/42/43/44/2/3/36/74, and Phase 1 around BRC-30/62/67/95/96 plus selected common templates and BRC-77/78. Treat BRC-100 wire compatibility as a layer above those primitives, then add BRC-52/103/104 auth, overlays, payments, tokens, multicast, and app protocols as separately testable capabilities. The main implementation risk is not missing a Go symbol; it is silently choosing the wrong side of a BRC/Go contradiction and then freezing that choice into Swift’s public types.
